## Control Unit Design


The control unit (CU) is the orchestrating logic of a processor: given the current instruction and processor state, it asserts the correct set of control signals to drive the datapath — register enables, ALU operation selects, multiplexer selects, memory read/write strobes, and program counter updates. The two fundamental implementation strategies — hardwired and microprogrammed — differ in how that mapping from state to signals is realized.

---

### What the Control Unit Must Produce

At each clock cycle (or sub-cycle), the CU receives:

- The opcode field of the current instruction (and possibly function code, addressing mode bits)
- State from the datapath: condition codes (zero, carry, overflow, negative), memory-ready signals, interrupt lines
- The current **control step** (for multi-cycle implementations)

It produces a vector of control signals. The width of this vector is determined by the datapath: a typical simple processor has 20–60 control lines; a complex out-of-order machine has hundreds.

---

### Hardwired Control

#### Principle

Control signals are generated by a combinational logic network (plus a state register for multi-cycle control). The mapping from (opcode, step, flags) → control signals is implemented directly in gates. No stored program or ROM lookup is involved.

The state machine view: the CU is a **finite state machine** whose inputs are the instruction register fields and datapath status bits, whose state register encodes the current control step, and whose outputs are the control signal vector.

For a single-cycle datapath the FSM degenerates to a purely combinational block — one state, outputs depend only on opcode. For multi-cycle, the FSM has one state per control step, and transitions encode the instruction's execution sequence.

#### Implementation

The standard realization uses a **one-hot state register** (one flip-flop per state) driving AND-OR arrays:

```
Control signal Cᵢ = OR over all (state, opcode) pairs that require Cᵢ to be asserted
```

Each output is a sum-of-products expression minimized with standard Boolean techniques (Karnaugh maps, Quine–McCluskey). The result is a two-level AND-OR network (or equivalently NAND-NAND), implementable in PLAs.

For an instruction set with n opcodes and m control steps, the PLA has:

- Input: log₂(m) step bits + log₂(n) opcode bits + k flag bits
- Output: one line per control signal

In practice, partial decoding and don't-cares reduce the AND-plane size substantially.

#### Performance and Properties

Since the output is a purely combinational function of the inputs (plus one register clock edge), hardwired control is **fast**: signal propagation is two gate delays through the AND-OR plane plus the register setup time. This is why RISC processors universally use hardwired control — the regular, fixed-length instruction format makes the combinational logic tractable.

The cost is **inflexibility**: adding an instruction requires modifying the gate network. For complex ISAs with many addressing modes and instruction variants (x86), the combinational logic becomes intractable to design and verify by hand.

### Microprogrammed Control

#### Principle

The control signal vector for each step of each instruction is stored as a **microinstruction** — a row in a ROM (the **control store**). Executing an instruction means sequencing through the corresponding microinstructions. The mapping from machine instruction to control store address is performed by a **mapping ROM** (or mapping logic).

The control store address register (**CAR**, also called the microprogram counter μPC) steps through microinstructions. At each cycle, the current microinstruction both drives the datapath and specifies the next CAR value.

#### Control Store Organization

Each microinstruction contains:

- **Operation fields**: one bit (or encoded group) per control signal, or per group of mutually exclusive signals
- **Sequencing field**: next-address, branch condition, jump-to-mapping, or fetch-next

The width of the microinstruction determines the degree of parallelism. Two encoding extremes:

|Style|Width|Decode required|Flexibility|
|---|---|---|---|
|Horizontal|Wide (100–200 bits)|Minimal|Maximum parallelism|
|Vertical|Narrow (16–32 bits)|Significant|Lower hardware cost|

**Horizontal microcode**: each bit directly drives one control signal. No decode delay. Allows any combination of signals to be asserted simultaneously, including combinations that make no architectural sense — correctness is the microprogrammer's responsibility. ROM width is large but access is fast.

**Vertical microcode**: control signals are encoded into fields; a local decoder expands each field to its one-hot form. Narrower ROM reduces cost and power; the decode stage adds latency. Intermediate encodings (diagonal microcode) balance width against decode cost.

#### Sequencing

The next microinstruction address is determined by one of:

- **Increment**: CAR ← CAR + 1 (sequential microinstructions)
- **Unconditional branch**: CAR ← address field of current microinstruction
- **Conditional branch**: CAR ← (condition ? addr_true : addr_false)
- **Fetch dispatch**: CAR ← mapping(IR[opcode]) — begins a new instruction's microroutine
- **Subroutine call/return**: a microsubroutine return register enables shared microroutines

The mapping from opcode to microprogram entry point is typically implemented as a small ROM indexed by opcode, or as an adder with a base address plus opcode offset.

#### Writable Control Store

Replacing the ROM with RAM (writable control store, WCS) allows microcode to be updated in the field — adding instructions, patching bugs, or implementing emulation of other ISAs. x86 processors have used this extensively; Intel's microcode update mechanism (loaded by the OS or BIOS) patches microcode in SRAM overlaying the factory ROM.

### Nanoprogramming

A second level of indirection below microcode. Microinstructions contain addresses into a **nanostore** rather than direct signal bits. Multiple microinstructions referencing the same signal pattern share a single nanoinstruction row. This reduces total ROM size when many microinstructions assert identical signal combinations, at the cost of an additional ROM access per cycle. Used in the Burroughs B1700 and some 1970s–80s minicomputers; rarely appears in contemporary design.

---

### Microcode in Contemporary x86

Modern x86 processors are not purely microprogrammed in the classical sense, but microcode persists in a hybrid form:

- Simple, common instructions (register-register ALU, branches) are decoded directly to μops by a hardwired **instruction decoder** in 1–2 cycles.
- Complex instructions (string operations, certain CISC instructions, some SSE/AVX variants) are flagged and handled by a **microcode sequencer** (MSROM on Intel nomenclature) that emits sequences of μops.
- The MSROM is shadowed by a small SRAM patch region, populated at boot from microcode update blobs. This is the mechanism through which Spectre/Meltdown mitigations and errata fixes are delivered.

The architectural boundary between "hardwired front-end" and "microprogrammed sequencer" is not visible at the ISA level.

---

### Design Trade-off Summary

|Criterion|Hardwired|Microprogrammed|
|---|---|---|
|Speed|1–2 gate delays per cycle|+1–2 ROM access cycles|
|Design effort|High (logic minimization, verification)|Lower (microprogramming)|
|ISA complexity tolerance|Low (RISC-suited)|High (CISC-suited)|
|Modifiability|Requires respinning silicon|Writable control store, microcode updates|
|Area|Smaller for simple ISAs|ROM dominates; larger for complex ISAs|
|Formal verification|Easier (finite combinational function)|Harder (microprogram correctness)|
|Historical use|RISC (MIPS, ARM, SPARC, RISC-V)|CISC (VAX, early x86, IBM 360/370)|
