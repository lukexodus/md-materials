## Batch Generation and Data Loaders for Training

### Why Batching Matters

Training on the full dataset at once is often impractical for large datasets due to memory constraints, and pure single-sample updates are typically noisy and computationally inefficient. Batch generation divides data into fixed-size chunks fed to a model iteratively during training. This is a standard, well-documented practice across ML frameworks, not a framework-specific quirk.

### Manual Batch Generation with NumPy

A basic batch generator can be built directly with NumPy indexing.

```python
import numpy as np

def batch_generator(X, y, batch_size=32, shuffle=True):
    n_samples = X.shape[0]
    indices = np.arange(n_samples)
    if shuffle:
        np.random.shuffle(indices)

    for start in range(0, n_samples, batch_size):
        end = min(start + batch_size, n_samples)
        batch_idx = indices[start:end]
        yield X[batch_idx], y[batch_idx]
```

```python
X = np.random.rand(100, 5)
y = np.random.randint(0, 2, size=100)

for X_batch, y_batch in batch_generator(X, y, batch_size=32):
    print(X_batch.shape, y_batch.shape)
```

**Output**
```
(32, 5) (32,)
(32, 5) (32,)
(32, 5) (32,)
(4, 5) (4,)
```

This output reflects the specific example above (100 samples, batch size 32): three full batches of 32 and one remainder batch of 4. This is deterministic arithmetic (100 = 3×32 + 4), not an inference.

### Handling the Last Batch

**Key Points**
- When `n_samples` is not evenly divisible by `batch_size`, the final batch will contain fewer samples than the rest, as shown above.
- Some training loops drop this final partial batch (common when batch normalization layers require a fixed batch size); others keep it. This is a design choice made by the pipeline author, not a fixed rule of NumPy or pandas.
- Dropping vs. keeping the last batch is a configurable behavior in most frameworks (e.g., PyTorch's `DataLoader` has a `drop_last` parameter). ### Batching from a pandas DataFrame

When source data lives in a DataFrame, batches are typically generated by slicing the index, then converting each slice to NumPy for the actual model input step.

```python
import pandas as pd

df = pd.DataFrame({
    "feature1": np.random.rand(100),
    "feature2": np.random.rand(100),
    "label": np.random.randint(0, 2, 100)
})

def df_batch_generator(df, batch_size=32, shuffle=True):
    indices = df.index.to_numpy()
    if shuffle:
        np.random.shuffle(indices)

    for start in range(0, len(indices), batch_size):
        batch_idx = indices[start:start + batch_size]
        batch_df = df.loc[batch_idx]
        X_batch = batch_df[["feature1", "feature2"]].to_numpy()
        y_batch = batch_df["label"].to_numpy()
        yield X_batch, y_batch
```

**Key Points**
- `.loc[batch_idx]` is used here rather than `.iloc` because `batch_idx` values are drawn from `df.index`, which may not correspond to positional order after shuffling.
- Repeated `.loc` slicing on very large DataFrames inside a tight loop [Inference] is likely to be slower than pre-converting the full DataFrame to a NumPy array once and then slicing that array directly, since `.loc` involves index-label lookup overhead on each call — but I have not benchmarked this claim and it is not confirmed for all DataFrame sizes or index types.

### Epochs vs. Batches vs. Steps

**Key Points**
- An **epoch** is one full pass through the entire training dataset.
- A **batch** (or mini-batch) is a subset of the dataset processed in a single forward/backward pass.
- A **step** (or iteration) refers to one update of model parameters, typically corresponding to one batch.
- The relationship: `steps_per_epoch = ceil(n_samples / batch_size)`, as reflected in the arithmetic example above.

$$\text{steps\_per\_epoch} = \left\lceil \frac{n_{\text{samples}}}{\text{batch\_size}} \right\rceil$$

### Shuffling Between Epochs

Reshuffling indices at the start of each epoch (rather than shuffling once before all training) is a common practice intended to reduce the chance that the model learns spurious patterns tied to a fixed data order.

```python
def epoch_batches(X, y, batch_size, n_epochs):
    n_samples = X.shape[0]
    for epoch in range(n_epochs):
        indices = np.random.permutation(n_samples)
        for start in range(0, n_samples, batch_size):
            batch_idx = indices[start:start + batch_size]
            yield epoch, X[batch_idx], y[batch_idx]
```

[Inference] Reshuffling per epoch is widely recommended in ML literature and framework documentation as a way to reduce overfitting to batch order, but I cannot verify the magnitude of this effect for any specific dataset or model without an actual benchmark.

### Using NumPy's `array_split` for Fixed Batch Counts

Instead of a fixed batch *size*, `np.array_split` divides an array into a fixed *number* of batches, which may be uneven in size.

```python
X = np.arange(20).reshape(10, 2)
batches = np.array_split(X, 3)

for b in batches:
    print(b.shape)
```

**Output**
```
(4, 2)
(3, 2)
(3, 2)
```

This is documented NumPy behavior: `array_split` distributes remainder rows across the earliest chunks rather than raising an error, unlike `np.split`, which requires equal-sized divisions and raises a `ValueError` otherwise.

### Streaming Batches for Data Too Large for Memory

For datasets that do not fit in memory, batches can be read incrementally from disk (e.g., using `pd.read_csv` with the `chunksize` parameter) instead of loading the full file first.

```python
chunk_iter = pd.read_csv("large_dataset.csv", chunksize=1000)

for chunk in chunk_iter:
    X_batch = chunk[["feature1", "feature2"]].to_numpy()
    y_batch = chunk["label"].to_numpy()
    # process batch
```

**Key Points**
- `chunksize` in `pd.read_csv` returns an iterator of DataFrames rather than loading the entire file at once, which is documented pandas behavior.
- This approach avoids holding the entire dataset in memory but reads sequentially, so shuffling across the *whole* dataset (not just within a chunk) requires additional strategy — such as pre-shuffling the file on disk or using a sampling buffer.
- [Unverified] I cannot verify the performance characteristics (e.g., throughput, I/O overhead) of chunked CSV reading for any specific hardware or file system without a direct benchmark.

### Handling Class Imbalance During Batching

When target classes are unevenly distributed, random batch sampling can produce batches with few or no examples of a minority class.

```python
import numpy as np

def stratified_batch_indices(y, batch_size, n_batches):
    classes = np.unique(y)
    class_indices = {c: np.where(y == c)[0] for c in classes}
    per_class = batch_size // len(classes)

    batches = []
    for _ in range(n_batches):
        batch_idx = []
        for c in classes:
            chosen = np.random.choice(class_indices[c], size=per_class, replace=True)
            batch_idx.extend(chosen)
        np.random.shuffle(batch_idx)
        batches.append(np.array(batch_idx))
    return batches
```

**Key Points**
- This forces each batch to contain a fixed proportion of each class, rather than relying on the natural (possibly imbalanced) distribution.
- `replace=True` allows minority-class samples to be reused within an epoch, which is a common but not universal strategy.
- [Inference] Stratified batching is commonly discussed in ML literature as a way to reduce training instability caused by class imbalance. I cannot verify the magnitude of this effect for any specific dataset without a direct benchmark, and this claim should not be treated as guaranteed to improve results in all cases.

### Combining Multiple Arrays in a Single Batch Generator

Pipelines often need to batch several aligned arrays together (e.g., features, auxiliary metadata, and targets) without losing row correspondence.

```python
def multi_array_batch_generator(batch_size, *arrays):
    n_samples = arrays[0].shape[0]
    indices = np.random.permutation(n_samples)

    for start in range(0, n_samples, batch_size):
        batch_idx = indices[start:start + batch_size]
        yield tuple(arr[batch_idx] for arr in arrays)
```

```python
X = np.random.rand(50, 4)
meta = np.random.rand(50, 2)
y = np.random.randint(0, 2, 50)

for X_b, meta_b, y_b in multi_array_batch_generator(16, X, meta, y):
    print(X_b.shape, meta_b.shape, y_b.shape)
```

**Key Points**
- All arrays passed in must share the same length along axis 0, or indexing will raise an `IndexError` or silently misalign data if shapes happen to match by coincidence.
- Using the same `batch_idx` array across all inputs is what keeps rows aligned — this is standard NumPy fancy-indexing behavior, not framework-specific.

### Validation and Test Set Batching Differences

**Key Points**
- Shuffling is typically disabled for validation and test batches, since evaluation order does not affect metric computation and disabling it makes results reproducible run-to-run.
- Batch size for evaluation can often be larger than training batch size, since no gradients need to be stored, reducing memory pressure. [Inference] This is a commonly cited practical benefit in ML engineering discussions, but actual achievable batch size depends on hardware and model architecture, so no specific multiplier can be stated as fact here.
- Dropping the last partial batch is generally discouraged during evaluation, since doing so would exclude some samples from the reported metric.
