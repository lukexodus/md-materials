## Sparse Vector Field Type

### Overview

`sparse_vector` is an Elasticsearch field type designed to store and index sparse vector representations, where each vector is expressed as a set of token-weight pairs rather than a dense array of floating-point numbers. Unlike `dense_vector`, which requires every dimension to be populated (even with zeros), `sparse_vector` only stores the non-zero dimensions, making it efficient for representations where the vocabulary space is large but any given document activates only a small subset of it.

The field type is primarily used to store output from sparse neural retrieval models, most notably Elastic's ELSER (Elastic Learned Sparse EncodeR), as well as other learned sparse embedding models that produce term-weight expansions instead of dense embeddings.

### Data Structure

A `sparse_vector` field stores data as a JSON object mapping tokens (strings) to weights (floating-point numbers):

```json
{
  "content_embedding": {
    "elastic": 1.23,
    "search": 0.98,
    "database": 0.45,
    "cloud": 0.12
  }
}
```

Each key represents a token from the model's learned vocabulary, and each value represents the relevance weight assigned to that token for the given document. Tokens with zero or near-zero weight are simply omitted, which is what makes the representation "sparse."

### Mapping Definition

```json
PUT my-index
{
  "mappings": {
    "properties": {
      "content_embedding": {
        "type": "sparse_vector"
      },
      "content": {
        "type": "text"
      }
    }
  }
}
```

No additional parameters are required for the basic mapping. The field does not support `index_options` or similarity tuning the way `dense_vector` does, since scoring uses standard inverted-index mechanics under the hood rather than vector-similarity math.

### How It Works Internally

`sparse_vector` fields are indexed using Lucene's standard inverted index structures, treating each token as a term and each weight as an impact score analogous to term frequency. [Inference] This is what allows sparse vector search to reuse Lucene's existing WAND (Weak AND) query execution and impact-based scoring machinery rather than requiring a dedicated vector index structure like HNSW — implementation details here may vary across Elasticsearch versions.

Because of this, sparse vector search does not require building or maintaining an approximate nearest-neighbor graph, and it integrates naturally with existing inverted-index query types.

### Populating the Field

Values are typically generated by running text through an inference pipeline (commonly using ELSER via an ingest pipeline with an `inference` processor), rather than being computed at query time by the user:

```json
PUT _ingest/pipeline/elser-pipeline
{
  "processors": [
    {
      "inference": {
        "model_id": ".elser_model_2",
        "input_output": {
          "input_field": "content",
          "output_field": "content_embedding"
        }
      }
    }
  ]
}
```

```json
PUT my-index/_doc/1?pipeline=elser-pipeline
{
  "content": "Elasticsearch provides powerful full-text search capabilities."
}
```

The ingest pipeline runs the ELSER model against `content` and writes the resulting token-weight map into `content_embedding` automatically.

### Querying with sparse_vector

The primary query used against `sparse_vector` fields is the `sparse_vector` query (which superseded the earlier `text_expansion` query):

```json
GET my-index/_search
{
  "query": {
    "sparse_vector": {
      "field": "content_embedding",
      "inference_id": "my-elser-endpoint",
      "query": "how does search relevance work"
    }
  }
}
```

**Key Points**

- `field` specifies the `sparse_vector` field to search against.
- `inference_id` references an inference endpoint (configured via the Inference API) used to expand the query text into token-weight pairs at query time.
- `query` is the raw natural-language text to be expanded.
- Alternatively, pre-computed query vectors can be supplied directly using the `query_vector` parameter instead of `query` + `inference_id`, bypassing inference at query time.

### Pruning and Tokens

Because learned sparse models can produce a large number of nonzero tokens per document, Elasticsearch supports token pruning to reduce index size and improve query latency:

```json
GET my-index/_search
{
  "query": {
    "sparse_vector": {
      "field": "content_embedding",
      "inference_id": "my-elser-endpoint",
      "query": "search relevance",
      "prune": true,
      "pruning_config": {
        "tokens_freq_ratio_threshold": 5,
        "tokens_weight_threshold": 0.4,
        "only_score_pruned_tokens": false
      }
    }
  }
}
```

- `tokens_freq_ratio_threshold` controls pruning based on how frequently a token appears relative to the average.
- `tokens_weight_threshold` controls pruning based on the token's weight relative to the document's maximum weight.
- `only_score_pruned_tokens` toggles whether scoring uses only the pruned-out (near-duplicate/high-frequency) tokens or the retained set. [Inference] Exact default values and pruning heuristics have shifted across recent Elasticsearch minor versions, so behavior should be checked against the version in use.

### Combining with Other Queries

`sparse_vector` queries commonly appear inside a `bool` query alongside lexical (`match`) or dense vector (`knn`) clauses to implement hybrid search:

```json
GET my-index/_search
{
  "query": {
    "bool": {
      "should": [
        {
          "sparse_vector": {
            "field": "content_embedding",
            "inference_id": "my-elser-endpoint",
            "query": "search relevance tuning"
          }
        },
        {
          "match": {
            "content": "search relevance tuning"
          }
        }
      ]
    }
  }
}
```

This pattern lets exact lexical matches and semantic/expansion matches both contribute to the final relevance score.

### Limitations and Considerations

- `sparse_vector` fields cannot be used in scripts via `doc['field']` the way numeric or keyword fields can; access patterns are restricted to the dedicated query types.
- Aggregations are not supported on `sparse_vector` fields.
- Storage overhead scales with the number of nonzero tokens per document, which is model-dependent; ELSER expansions are typically much smaller than the full vocabulary but still larger than a dense embedding's fixed dimensionality in raw term count. [Inference] Actual storage comparisons depend on the specific model and pruning configuration used.
- The field type historically replaced an earlier `rank_features`-based approach for similar use cases, and the `text_expansion` query type was deprecated in favor of `sparse_vector` as of Elasticsearch 8.15. [Unverified] Confirm exact deprecation version against current release notes, as this may have been adjusted in later patches.
