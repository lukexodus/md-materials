## Multi-fields in Elasticsearch

---

### What Are Multi-fields?

In Elasticsearch, a **multi-field** mapping allows a single field to be indexed in more than one way simultaneously. The same source value is processed and stored under multiple sub-fields, each with its own type, analyzer, or indexing configuration.

Multi-fields do not duplicate the value in `_source` — the original value is stored once. The additional sub-fields exist only in the index structures (inverted index, doc values) used at search and aggregation time.

---

### Why Multi-fields Are Needed

A fundamental tension exists in Elasticsearch field types:

- `text` fields are analyzed — suitable for full-text search, but not for sorting, aggregations, or exact matching
- `keyword` fields are not analyzed — suitable for exact matching, sorting, and aggregations, but not for relevance-based full-text search

Without multi-fields, you would be forced to choose one behavior per field, or maintain two separate fields with different names fed by the same source value. Multi-fields resolve this by indexing the same value in both ways under a single field name.

---

### Defining Multi-fields

Multi-fields are defined using the `fields` parameter within a field mapping.

**Basic syntax:**

```json
"<field_name>": {
  "type": "<primary_type>",
  "fields": {
    "<sub_field_name>": {
      "type": "<secondary_type>"
    }
  }
}
```

**Example — `text` with a `keyword` sub-field:**

```json
PUT /articles
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "english",
        "fields": {
          "keyword": {
            "type": "keyword",
            "ignore_above": 256
          }
        }
      }
    }
  }
}
```

- `title` — analyzed with the `english` analyzer; used for full-text search
- `title.keyword` — stored as-is; used for exact match, sorting, and aggregations

---

### Accessing Sub-fields

Sub-fields are referenced using dot notation: `<field>.<sub_field>`.

**Full-text search on the parent field:**

```json
GET /articles/_search
{
  "query": {
    "match": {
      "title": "introduction to machine learning"
    }
  }
}
```

**Exact match or aggregation on the keyword sub-field:**

```json
GET /articles/_search
{
  "aggs": {
    "top_titles": {
      "terms": {
        "field": "title.keyword",
        "size": 10
      }
    }
  }
}
```

**Sorting on the keyword sub-field:**

```json
GET /articles/_search
{
  "sort": [
    { "title.keyword": "asc" }
  ]
}
```

### Common Multi-field Patterns

#### text + keyword (most common)

The default pattern generated by dynamic mapping for string fields. Enables both full-text search and aggregation/sorting.

```json
"product_name": {
  "type": "text",
  "fields": {
    "keyword": { "type": "keyword", "ignore_above": 256 }
  }
}
```

#### text with multiple analyzers

A single field indexed with different analyzers for different search behaviors — for example, one for language-specific stemming and one for exact phrase matching.

```json
"description": {
  "type": "text",
  "analyzer": "english",
  "fields": {
    "standard": {
      "type": "text",
      "analyzer": "standard"
    },
    "exact": {
      "type": "keyword"
    }
  }
}
```

- `description` — uses English analyzer (stemming, stopwords)
- `description.standard` — uses standard tokenizer (no stemming)
- `description.exact` — exact keyword match

#### keyword + wildcard

For fields where both exact aggregation and wildcard/regex pattern queries are needed.

```json
"log_path": {
  "type": "keyword",
  "fields": {
    "wildcard": {
      "type": "wildcard"
    }
  }
}
```

- `log_path` — used for term filters and aggregations
- `log_path.wildcard` — used for `wildcard` or `regexp` queries efficiently

#### text + completion

For fields that serve both full-text search and autocomplete suggestions.

```json
"product_name": {
  "type": "text",
  "fields": {
    "suggest": {
      "type": "completion"
    }
  }
}
```

- `product_name` — searched with `match` queries
- `product_name.suggest` — queried with the suggest API

#### text + token_count

For fields where both the content is searchable and the token length needs to be filterable.

```json
"body": {
  "type": "text",
  "analyzer": "standard",
  "fields": {
    "length": {
      "type": "token_count",
      "analyzer": "standard"
    }
  }
}
```

- `body` — full-text searchable
- `body.length` — stores the number of tokens; can be used in range filters

---

### ignore_above on keyword Sub-fields

The `ignore_above` parameter on a `keyword` sub-field instructs Elasticsearch to skip indexing values that exceed the specified character length. Values that exceed the limit are still stored in `_source` but are not indexed.

```json
"tag": {
  "type": "text",
  "fields": {
    "keyword": {
      "type": "keyword",
      "ignore_above": 256
    }
  }
}
```

> [Inference] Setting `ignore_above` on keyword sub-fields may help avoid indexing unexpectedly long strings that would otherwise inflate the index with low-utility terms. The appropriate limit depends on the data. Behavior may vary.

### Adding Multi-fields to an Existing Mapping

Multi-fields can be added to fields that are already mapped, without requiring reindexing for new documents. However, existing documents will not automatically have the new sub-field populated — they need to be reindexed to appear in the new sub-field.

**Adding a sub-field to an existing field:**

```json
PUT /articles/_mapping
{
  "properties": {
    "title": {
      "type": "text",
      "fields": {
        "keyword": {
          "type": "keyword",
          "ignore_above": 256
        }
      }
    }
  }
}
```

> [Inference] Documents indexed before the sub-field was added will not have values in the new sub-field unless explicitly reindexed via the `_reindex` API. Behavior may vary.

---

### Multi-fields and `_source`

Multi-fields do not affect the `_source` document. The `_source` always contains the original field value under the top-level field name only. Sub-field names do not appear in `_source`.

**Example document indexed:**

```json
{ "title": "Elasticsearch in Practice" }
```

**`_source` returned:**

```json
{ "title": "Elasticsearch in Practice" }
```

The values indexed under `title.keyword` or `title.standard` exist only in the index structures and are not visible in `_source`.

---

### Nesting Multi-fields Inside object and nested Types

Multi-fields can be defined on fields within `object` or `nested` types, following the same pattern.

```json
"author": {
  "type": "object",
  "properties": {
    "name": {
      "type": "text",
      "fields": {
        "keyword": { "type": "keyword" }
      }
    }
  }
}
```

- `author.name` — full-text searchable
- `author.name.keyword` — exact match, sortable, aggregatable

---

### Querying Across Multiple Sub-fields

The `multi_match` query allows a single query string to be run against multiple fields simultaneously, including sub-fields.

```json
GET /articles/_search
{
  "query": {
    "multi_match": {
      "query": "machine learning",
      "fields": ["title", "title.standard", "description"]
    }
  }
}
```

Scores from each field match are combined according to the `type` parameter of `multi_match` (e.g., `best_fields`, `most_fields`, `cross_fields`).

---

### Considerations and Trade-offs

| Consideration | Detail |
|---|---|
| Storage overhead | Each sub-field maintains its own index structure; more sub-fields increase index size |
| Indexing throughput | [Inference] Additional sub-fields add processing cost per document at index time; impact depends on field count and volume |
| Query clarity | Sub-field dot notation keeps field intent explicit at the query layer |
| Maintenance | Adding sub-fields to existing indices does not backfill old documents |
| `_source` unchanged | Sub-fields are invisible in source; consumers of raw documents are unaffected |

---

### Best Practices

- **Define `text` + `keyword` multi-fields explicitly in production mappings** rather than relying on dynamic mapping defaults, so you can control `ignore_above`, analyzers, and other parameters.
- **Only define sub-fields you will actually use.** Each sub-field adds index overhead. A `keyword` sub-field on a free-text field that is never aggregated or sorted is unnecessary cost.
- **Use a consistent sub-field naming convention** across your indices. `.keyword` for keyword sub-fields and named sub-fields (`.english`, `.standard`) for analyzer variants reduces confusion at query time.
- **After adding a new sub-field to an existing index, reindex** if you need existing documents to be searchable via that sub-field.
- **Avoid deeply chained multi-fields.** While Elasticsearch permits sub-fields on sub-fields in some configurations, the added complexity rarely justifies the use case.
