## Log Message Format


### Structured Logging and Serialization

The industry standard for modern logging is structured logging, specifically outputting logs as serialized JSON objects rather than unstructured text lines. Unstructured text requires complex, brittle Regex parsing rules at the ingestion layer (Logstash, Fluentd).

- **Machine Readability:** JSON allows log aggregators (Elasticsearch, Splunk, Datadog) to automatically index fields without custom parsers. This enables high-speed querying on specific attributes (e.g., `http.response_time > 500`) rather than slow full-text searches.
    
- **Field Type Consistency:** Enforce strict typing within the log structure. A field named `user_id` must effectively be treated as a string or an integer consistently across all services. Mixed types (string in one service, integer in another) cause schema collisions in indexing backends, resulting in dropped logs or "mapper parsing exceptions."
    
- **Contextual Payloads:** Do not interpolate variables into the `message` string (e.g., `log.info("User " + userId + " logged in")`). Instead, pass the message as a static template and the variables as a separate context object.
    
    - _Anti-Pattern:_ `"message": "Processed order 12345 in 20ms"`
        
    - _Best Practice:_ `"message": "Order processed", "order_id": "12345", "duration_ms": 20`
        
    - This ensures unique message signatures remain low cardinality, optimizing storage and categorization.
        

### Canonical Schema and Taxonomy

Adopting a unified logging taxonomy across the entire microservices architecture is critical for observability. Without a shared schema, cross-service debugging becomes impossible.

- **Standard Fields:** Every log entry must contain a baseline set of metadata:
    
    - `@timestamp`: ISO-8601 formatted with high precision (nanoseconds preferred) and UTC time zone.
        
    - `level`: Standardized severity (DEBUG, INFO, WARN, ERROR, FATAL).
        
    - `service.name`: The immutable identifier of the application.
        
    - `host.name` / `container.id`: Infrastructure provenance.
        
- **OpenTelemetry / ECS:** Align field naming with industry standards like the Elastic Common Schema (ECS) or OpenTelemetry Semantic Conventions. Use `http.request.method` instead of `method`, `httpRequestType`, or `req_method`. This facilitates the use of off-the-shelf dashboards and anomaly detection rules.
    

### Correlation and Causality

In distributed systems, a log entry in isolation is often useless. Logs must explicitly link to the broader request lifecycle.

- **Trace Context Injection:** All log entries must include `trace_id` and `span_id`. These identifiers should automatically propagate from incoming HTTP headers (W3C Trace Context) into the logging context (MDC/ThreadLocal). This allows an operator to filter all logs across N microservices generated by a single user action.
    
- **Causality Chains:** When logging an error caused by an upstream failure, the log must capture the `correlation_id` of the upstream request to enable root cause analysis.
    

### Sanitization and Compliance

Logging is a primary vector for data leaks. Raw logging of request payloads often inadvertently captures PII (Personally Identifiable Information), PCI (Payment Card Information), or credentials.

- **Data Masking at Source:** Implement robust masking strategies _within_ the application's serialization layer, before the data leaves the process memory. Relying on downstream log collectors to scrub data is insufficient, as the sensitive data still traverses the network and may be persisted in intermediate buffers.
    
- **Allow-listing vs. Block-listing:** Prefer an explicit allow-list of safe fields to log. Block-listing is error-prone; when a developer adds a new field like `social_security_number` to a user object, a block-list based logger will unknowingly dump it until updated.
    
- **GDPR/Right to be Forgotten:** Avoid logging distinct PII (e.g., email addresses) as indexed keys. If identifying users is necessary for debugging, log a salted hash of the identifier or a synthetic user UUID, ensuring the logs themselves do not become a system of record for user data.
    

### Exception Handling and Stack Traces

Logging exceptions requires specific formatting to preserve the diagnostic utility of the stack trace without polluting the index.

- **Structured Error Objects:** Do not `toString()` an exception into the `message` field. Serialize the exception into a dedicated `error` object containing:
    
    - `error.type`: The class name of the exception.
        
    - `error.message`: The exception message.
        
    - `error.stack_trace`: The full stack trace as a single string field (multi-line strings are handled by JSON parsers).
        
- **Root Cause Traversal:** If using wrapped exceptions, the logger must recursively traverse the `caused_by` chain to capture the original source of the error, not just the generic top-level handler wrapper.
