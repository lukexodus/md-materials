## Contextual Information


In robust software architecture, data is meaningless without context. "Contextual Information" refers to the metadata and state snapshots that accompany execution flows, errors, and audit logs. High-quality code explicitly manages this context to ensure observability, debuggability, and reliable distributed tracing.

### Structured Logging and Mapped Diagnostic Context (MDC)

Standard text-based logging (`log.info("User failed login")`) is insufficient for modern distributed systems. Context must be structured and queryable.

- **MDC (Mapped Diagnostic Context):** Utilize MDC (available in Java via SLF4J/Logback, .NET via Serilog, etc.) to bind contextual data to the executing thread. Once set, this data automatically enriches every log line generated by that thread without polluting method signatures.
    
- **Structured Output:** Logs must be emitted as JSON objects, not raw strings. This allows log aggregators (ELK, Splunk, Datadog) to index contextual fields efficiently.
    
- **Required Fields:**
    
    - **Correlation ID:** A unique identifier per external request, propagated across all microservices.
        
    - **Tenant/User ID:** Identifies the actor.
        
    - **Source Context:** Class name, method name, or module.
        
    - **Environment:** Region, availability zone, container ID.
        

**Anti-Pattern:** String concatenation for context.

- _Bad:_ `log.error("Error processing order " + orderId);`
    
- _Good:_ `log.error("Error processing order", kv("orderId", orderId), kv("duration_ms", duration));`
    

### Error Handling and Exception Enrichment

Exceptions must carry state, not just stack traces. A generic `NullPointerException` is a quality failure; an exception detailing _which_ variable was null during _what_ operation constitutes high-quality code.

- **Contextual Wrapping:** When catching and re-throwing exceptions across architectural boundaries, wrap the lower-level exception with a higher-level custom exception that adds local context.
    
- **Exception Payload:** Custom exception classes should possess fields for relevant IDs (e.g., `failedRowId`, `queryParameters`) rather than burying this information in the error message string.
    
- **The "Cause" Chain:** Always preserve the original root cause exception to maintain the full stack trace for deep debugging.
    

### Distributed Context Propagation

In microservices, execution jumps across network boundaries. Context must survive the jump.

- **W3C Trace Context:** Adhere to the W3C standard for `traceparent` and `tracestate` headers. This ensures interoperability between different tracing tools (OpenTelemetry, Jaeger, Zipkin).
    
- **Header Forwarding:** Middleware must automatically capture specific HTTP headers (Authorization, X-Request-ID) from incoming requests and inject them into downstream service calls.
    
- **Baggage:** Use the "Baggage" pattern (common in OpenTelemetry) to propagate arbitrary key-value pairs (e.g., `is_vip_user=true`) across the entire call graph, enabling deep analytical filtering without altering API signatures.
    

### Execution Context Management

Managing how context is stored and accessed within the application runtime is critical for thread safety and performance.

- **Thread-Local Storage (TLS):** In synchronous, thread-per-request models (e.g., Spring Boot, classic ASP.NET), context is typically stored in ThreadLocal variables.
    
    - _Risk:_ Memory leaks in thread pools if context is not rigorously cleared (`finally { context.clear(); }`) after request processing.
        
- **Explicit Context Passing (Go/Node.js):** In asynchronous or coroutine-based models, ThreadLocal is dangerous or impossible.
    
    - _Standard:_ Explicitly pass a Context object (e.g., Go's `context.Context`) as the first argument to every function. This object carries deadlines, cancellation signals, and request-scoped values.
        
    - _Discipline:_ Do not store Context in struct fields; it must flow through the call stack.
        

### Security and Auditing

Context provides the "Who, When, and Where" for security incidents.

- **Non-Repudiation:** Audit logs must contain immutable context regarding the identity provider, the scope of permissions at the time of access, and the specific API endpoint version accessed.
    
- **Sanitization:** Contextual information often contains PII (Personally Identifiable Information). Implement strict strict redacting filters (e.g., masking credit card numbers or JWT tokens) _before_ the context is written to disk or sent to a centralized logging server.
