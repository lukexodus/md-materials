## Logging for debugging


Logging for debugging is the practice of emitting telemetry data from an application to reconstruct its state and execution flow after the fact. Unlike interactive debugging (breakpoints), logging persists the narrative of the application's behavior, allowing developers to diagnose issues in environments where they cannot pause execution (e.g., production). Effective debug logging transforms opaque failures into solvable root causes by prioritizing structure, context, and appropriate granularity.

**Key Points**

- **Structured Logging:** Modern logging should not be plain text (e.g., "User failed"). It must be structured data (JSON) containing key-value pairs. This allows log aggregation tools (Splunk, ELK Stack, Datadog) to index, search, and visualize data fields like `user_id`, `request_id`, or `error_code`.
    
- **Log Levels:** Strict adherence to levels prevents noise.
    
    - **DEBUG:** Granular information for diagnosing logic (e.g., variable state, loop iterations). usually disabled in production.
        
    - **INFO:** High-level operational events (e.g., "Service started", "Job completed").
        
    - **WARN:** Unexpected but recoverable events (e.g., "Retry attempt 1", "Deprecated API usage").
        
    - **ERROR:** Operations that failed but did not crash the app (e.g., "Database timeout", "Payment declined").
        
    - **FATAL:** Catastrophic errors forcing a shutdown.
        
- **Context and Correlation:** In microservices or concurrent systems, logs must include a **Correlation ID** (or Trace ID). This unique identifier is passed between services, allowing a developer to filter all logs generated by a single specific user request across the entire fleet.
    
- **Lazy Evaluation:** Constructing complex log strings consumes CPU and memory. Use parameterized logging (e.g., `log.debug("Data: {}", expensive_to_string_obj)`) so string interpolation only happens if the DEBUG level is actually enabled.
    
- **Sanitization:** strictly scrub PII (Personally Identifiable Information), secrets, and tokens. Logging a password or API key is a critical security vulnerability.
    

**Example**

The following comparison illustrates the difference between "printf debugging" (unstructured, vague) and production-grade structured logging.

_Bad Practice (Unstructured & Vague):_

JavaScript

```
// Problem: Hard to parse programmatically, lacks context, 
// and string concatenation happens even if logging is off.
function processPayment(user, amount) {
    console.log("Processing payment for user " + user.id); 
    try {
        charge(user, amount);
    } catch (e) {
        console.log("Error: " + e); // What user? What amount? When?
    }
}
```

_Good Practice (Structured & Contextual):_

JavaScript

```
const logger = require('pino')(); 

function processPayment(user, amount, traceId) {
    // Context object allows filtering by traceId later
    const context = { 
        trace_id: traceId, 
        user_id: user.id, 
        amount: amount, 
        currency: 'USD' 
    };

    logger.debug(context, "Payment processing started");

    try {
        charge(user, amount);
        logger.info(context, "Payment successful");
    } catch (error) {
        // Log the full stack trace and the error message as separate fields
        logger.error({ 
            ...context, 
            err: error.message, 
            stack: error.stack,
            error_code: error.code 
        }, "Payment transaction failed");
    }
}
```

**Output**

When the "Good Practice" code runs, the output is a machine-readable JSON object. This allows an SRE to query `log.level == "error" AND user_id == "42"`.

JSON

```
{
  "level": 30,
  "time": 1678892345000,
  "msg": "Payment transaction failed",
  "trace_id": "abc-123-xyz",
  "user_id": 42,

  "stack": "Error: Insufficient Funds\n    at charge (/app/payment.js:12:7)...",

  "v": 1
}
```

**Conclusion**

Logging is the primary interface for understanding an application's behavior in the wild. High-quality logging balances volume (cost) with utility (debuggability). By adopting structured logging and consistent levels, developers move from reading text files to querying a database of events, drastically reducing Mean Time To Recovery (MTTR).
